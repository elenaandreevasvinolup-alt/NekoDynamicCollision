# Neko Dynamic Collision (NDC) — развёртывание и руководство

Запечённая коллизия на выпуклых телах для Unity. Вся дорогая работа выполняется в
редакторе; среда выполнения только загружает и маршрутизирует. Скелетный персонаж или статический меш
превращается в набор выпуклых тел по костям и регионам с **нулевыми затратами на кадр**,
встроенными событиями разделов и физическими материалами по регионам, нарисованными кистью.

Сам компонент не содержит сгенерированного кода, атрибутов и не имеет во время выполнения
зависимости от редакторской части плагина. Удалите `Editor/` — и среда выполнения продолжит работать.

<a id="sec-partA"></a>
# Часть A — Быстрое развёртывание

<a id="sec-1"></a>
## 1. Запеките первого персонажа

1. Выберите персонажа и добавьте компонент **Dynamic Collision**
   (`Add Component → Neko → Dynamic Collision` или меню `GameObject`).
   При создании компонент находит свой `SkinnedMeshRenderer` и создаёт одну
   группу материалов по умолчанию. Вам не нужно ничего заполнять.
2. Нажмите **Запечь** в инспекторе.
3. Выпуклые тела появляются в окне Scene как каркас в позе привязки. Выберите персонажа, чтобы
   их увидеть; гизмо по умолчанию следует за вашим выделением.

Запекание создаёт три вида ассетов рядом со сценой:

```
Assets/NekoDynamicCollision/Baked/<SceneName>/
├── <Object>_Baked.asset        hull meshes + bind matrices + edges + volumes
├── <Object>_Paint.asset        the brush labels, one byte per triangle
└── Materials/DYC_<preset>.physicMaterial
```

Меши выпуклых тел — это подассеты `_Baked.asset`, поэтому они переносятся вместе с ним и
сохраняются в режиме Play и в сборках. Во время выполнения ничего не пересчитывается.

<a id="sec-2"></a>
## 2. Нарисуйте регионы материалов

Кисть — это то, что делает возможным «один объект, несколько физических материалов».

1. Откройте окно запекания (`NekoWorks → NekoDynamicCollision → Open Main Window`).
2. Перейдите на вкладку **Материалы** и добавьте группу для каждого региона — например,
   `Hard` и `Soft`. Выберите пресет для каждой.
3. Перейдите на вкладку **Кисть**, выберите группу для рисования, нажмите **Начать покраску**.
4. В окне Scene проведите по граням, которые хотите отнести к этой группе. Нарисованные
   треугольники сразу заливаются цветом группы.
5. Запеките повторно. Теперь каждый регион получает свои выпуклые тела со своим физическим материалом.

Рисовать можно только при остановленном режиме Play и когда окно Animation не
воспроизводит предпросмотр. Сама поза не важна — метки хранятся по индексу треугольника,
поэтому текущая поза не имеет значения.

<a id="sec-3"></a>
## 3. Путь за 10 минут

| Минута | Что делать |
|---|---|
| 0–2 | Добавьте компонент, нажмите Запечь, посмотрите на гизмо. |
| 2–4 | Откройте вкладку **Здоровье**, исправьте всё, что отмечено красным. |
| 4–6 | Откройте вкладку **Запекание**, посмотрите на число покрытия. Ниже ~95 % — повысьте точность. |
| 6–9 | Добавьте группу материалов для каждого региона, нарисуйте её, запеките повторно. |
| 9–10 | Задайте слой взаимодействия `Bullet`, привяжите имя события, проверьте в режиме Play. |

<a id="sec-partB"></a>
# Часть B — Руководство

<a id="sec-4"></a>
## 4. Основные понятия

### Выпуклые тела, а не «суп» из треугольников

Динамический (не кинематический) `Rigidbody` не может использовать невыпуклый `MeshCollider` — это
ограничение PhysX, а не Unity. Поэтому каждая форма коллизии для движущегося тела
должна быть выпуклой. NDC запекает **выпуклые тела** и передаёт Unity само выпуклое тело, а не
исходное подмножество треугольников, поэтому число вершин никогда не достигает
потолка PhysX в 255.

### Почему жёстких относительно костей выпуклых тел достаточно

В позе привязки `bone.localToWorldMatrix · bindposes[i] = I`. Скиннинг вершины,
взвешенной на 100 % по одной кости, поэтому даёт ровно меш в позе привязки. Иными
словами: **выпуклое тело, запечённое в локальном пространстве кости, бит в бит совпадает с тем,
что дал бы пересчёт каждый кадр**, для жёстко взвешенных вершин.

Различаются только вершины со смешанными весами — те, что пересекают сустав. Они покрываются
соседними выпуклыми телами, которые перекрываются по построению. Поэтому NDC может быть бесплатным во
время выполнения и при этом точным там, где это важно.

### Пространственная кластеризация, а не разбиение по порядку индексов

NDC группирует треугольники по положению (инициализация по самым удалённым точкам плюс рост в стиле
Дейкстры по смежности рёбер). Альтернатива — брать треугольники в порядке индексов — даёт
выпуклые тела, которые перекрываются и охватывают пустоту, и чем больше тел вы запросите, тем хуже.

### Разделы и группы материалов

Две независимые оси:

- **Раздел** — *где*. Одна кость (режим Skin) или весь меш (режим Mesh).
  Дочерний раздел всегда имеет приоритет над предком, поэтому события никогда не отправляются дважды.
- **Группа материалов** — *что*. Набор граней, использующих один физический материал и одну
  плотность, созданный рисованием.

Выпуклое тело — это пересечение одного раздела и одной группы материалов. Если у группы нет
нарисованных граней внутри данной кости, для этой пары тело не создаётся.

### Что делает среда выполнения

1. Загружает запечённый набор.
2. Создаёт по одному скрытому дочернему объекту на каждое выпуклое тело под нужной костью, с единичным
   трансформом, и назначает выпуклый `MeshCollider`.
3. Строит таблицу соответствия `Collider → hull`.
4. Размещает `Dyc_Relay` на каждом `Rigidbody`, которому принадлежит выпуклое тело.
5. Настраивает слои, самоколлизию и массу.

Затем она останавливается. Никакой работы в `Update` нет, кроме необязательного опроса триггеров и
проверки расстояния для LOD.

<a id="sec-5"></a>
## 5. Установка и требования

- Unity 2022.3 или новее.
- Скопируйте `Assets/NekoDynamicCollision` в свой проект. Настраивать
  ничего не нужно; сборки ограничены определениями сборок.
- Две сборки:
  - `Neko.DynamicCollision.Runtime` — компонент, ретранслятор, опрос триггеров, структуры
    событий и фасад интеграции. Никогда не ссылается на `UnityEditor`.
  - `Neko.DynamicCollision.Editor` — запекание, математика выпуклых тел, кластеризация, кисть,
    гизмо, проверка состояния, пресеты и окно. Только для платформы редактора.

<a id="sec-8"></a>
## 8. Точность

Один регулятор, четыре ступени. Внутри он разворачивается в четыре значения:

| Точность | Треугольников на выпуклое тело | Выпуклых тел на раздел | Перекрытие шва | Порог веса |
|---|---|---|---|---|
| Coarse | 120 | 1 | 4.0 мм | 0.35 |
| Normal | 250 | 2 | 3.0 мм | 0.25 |
| Fine | 500 | 4 | 2.0 мм | 0.15 |
| Ultra | 1000 | 8 | 1.0 мм | 0.05 |

- **Треугольников на выпуклое тело** ограничивает, сколько геометрии может поглотить одно тело. Больше треугольников
  на тело — значит меньше крупных, но более свободных выпуклых тел.
- **Выпуклых тел на раздел** — целевое число кластеров на раздел. Больше кластеров
  — более плотное прилегание и больше коллайдеров.
- **Перекрытие шва** раздувает каждое тело наружу, чтобы соседние регионы перекрывались,
  а не оставляли зазор. Перекрытие безопасно (попадание никогда не теряется, а дедупликация
  в пределах кадра предотвращает двойные события); зазор — нет.
- **Порог веса** отбрасывает вершины, вес которых для доминирующей кости ниже
  этого значения. Чем выше, тем плотнее и «жёстче корректно» выпуклое тело.

Число вершин выпуклого тела никогда не превышает число уникальных вершин кластера, которое
ограничено 250 — безопасно ниже предела PhysX в 255. Проверка состояния помечает любое
тело выше 255 красным.

### 8.1 Режим «выпуклый» выполняет декомпозицию — за пределами CC и встроенного сложного коллайдера

В режиме **выпуклый** вогнутый меш разрезается на выпуклые части вдоль своих вогнутостей. Это та же идея, что у встроенного сложного коллайдера и инструментов в стиле V-HACD (CC): возьмите любой меш и получите выпуклые части. NDC сохраняет широту и поднимает потолок:

| | Сложный коллайдер / CC | NDC |
|---|---|---|
| Любой меш | да | да |
| Хорошо оптимизирован | да | да — фоновая задача запекания, прогресс, отмена, бюджеты на кость |
| Части уважают суставы | **нет** — чисто геометрически, плечо может проглотить руку | **да** — части несут метки костей из поля весов |
| Пригоден на движущемся теле | **нет** — PhysX отказывает невыпуклому коллайдеру на некинематическом `Rigidbody` | **да** — на выходе выпуклое тело |
| Стоимость в рантайме | кукинг коллайдера при загрузке | ноль — запечено в ассеты |
| Запасной вариант | — | пространственная кластеризация, поэтому вырожденный меш всё равно получает коллайдер |

Окно Expert сообщает, пришли ли части из **декомпозиции** (разрез вдоль вогнутостей) или из **пространственной кластеризации** (запасной вариант), так что разница — это число, а не догадка.

**Насколько мелкий разрез** задаёт один ползунок — **Decomposition detail** —, а размер вокселя в миллиметрах виден в числовом поле прямо под ним. Это две проекции *одного* числа, поэтому они всегда согласованы: потяните ползунок — поле следует за ним, введите значение в поле — ползунок сдвинется. Второй настройки, которую нужно синхронизировать, нет.

- **Слева** — грубый воксель: частей меньше, они крупнее. Дешевле всего и обычно достаточно для реквизита.
- **Справа** — самый мелкий воксель. Части следуют за поверхностью, поэтому стоимость **совпадает с невыпуклым режимом**: мельче ничего не выиграть, только дороже.

Таблица точности выше относится тогда к *подгонке кластеров* — насколько плотно садится каждая часть, — а не к тому, сколько коллайдеров вы получите.

Один и тот же ползунок есть в обоих режимах: выпуклая декомпозиция и невыпуклое упрощение — два способа ответить на один вопрос: *сколько детализации мне нужно*.

### 8.2 Невыпуклая детализация — это один ползунок

Переключите **Collider shape → Non-convex surface**, и появится ползунок **Surface detail**.

| Ползунок | Результат |
|---|---|
| Крайне слева | Сильно упрощённая поверхность — мало треугольников, заметны грани |
| Посередине | Хороший компромисс: форма читается правильно, коллайдер остаётся дешёвым |
| **Крайне справа** | **Никакого упрощения** — поверхность берётся из меша как есть |

Почему это ползунок, а не число треугольников: «сколько треугольников на часть» нельзя выбрать разумно, не зная, сколько их у меша, — 500 это грубо для торса и точно для пальца. Ползунок отвечает на единственный вопрос, который пользователь действительно может задать: *насколько мне важна точная форма*. Крайнее правое положение — не «почти точно», а точно: упрощение отключено полностью.

Мелкие кластеры не упрощаются никогда, независимо от ползунка, — если стянуть тонкий палец на грубую сетку, он схлопнется в ничто, а пустой коллайдер хуже дорогого.

И режим Skin, и режим Mesh используют один и тот же ползунок.

<a id="sec-9"></a>
## 9. Кисть

Кисть не «исключает» грани. Она **помечает** их, и метки управляют запеканием.

| Действие | Эффект |
|---|---|
| Перетаскивание левой кнопкой | Назначить текущую группу треугольникам под курсором |
| Shift + перетаскивание | Стереть обратно до группы 0 и снять флаг рисования |
| Колесо мыши | Радиус кисти |
| Переключатель `X` (в окне) | Зеркально отражать каждый мазок относительно локального X = 0 объекта |

Настройки: радиус, X-Ray (игнорировать обратные грани), зеркало по X.

Требования, которые проверяются с явным сообщением, а не молчаливым сбоем:

1. Режим Play должен быть остановлен.
2. Окно Animation не должно воспроизводить предпросмотр.

Риг **не** должен находиться в позе привязки. Кисть пускает луч по мешу
в его **текущей** позе; поскольку скиннинг никогда не меняет топологию, индексы треугольников
сопоставляются один к одному, и метки остаются корректными.

Если вы всё же хотите вернуть риг в позу привязки, кнопка **Сбросить в bind pose** решает
локальные трансформы из `bindposes[i].inverse` и записывает их обратно, с поддержкой undo.

<a id="sec-10"></a>
## 10. Группы материалов и пресеты

Каждая группа несёт `PhysicMaterial`, плотность в кг/м³, необязательное имя события
и множитель урона.

**Пресеты.** 224 пресета в 14 категориях (Metal, Ceramic, Plastic, Glass, Wood,
Stone & Concrete, Rubber, Fabric & Leather, Body parts, Tissue & organs, Organic, Ice,
Food, Other) — см. [Приложение A](#appendix-a-physic-material-presets).
Применение пресета создаёт настоящий ассет `.physicMaterial` в `Baked/<Scene>/Materials/`,
так что на него можно ссылаться, сравнивать его, класть в Addressables и передавать художнику.

**Кузница материалов.** Строка таблицы отвечает «из чего это сделано»; кузница отвечает
«что это сейчас». Она умножает базовый пресет на **состояние поверхности** (Dry, Wet,
Oiled, Bloody, Sweaty, Icy, Frozen, Dusty, Rough, Polished, Rusted, Worn, Charred,
Clothed, Armoured). `Dry` — тождество, поэтому рядом с `steel` никогда не появляется
`steel_dry`. Трение умножается и на покоящийся, и на динамический коэффициент сразу.

**Части тела выводятся, а не вписываются.** «Части тела» и «Ткани и органы» — вообще не
строки таблицы: они считаются из смеси тканей. Плотность складывается, мягкость
складывается плюс слагаемое подушки, а трение и отскок следуют из мягкости. «Грудь» —
это 80 % жира + 10 % мышцы + 10 % кожи; «череп» — 95 % кости + 5 % кожи.

**Генерация ассетов.** *Создать ассеты вариантов* пишет по одному `.physicMaterial` на
состояние в `Baked/<Scene>/Materials/`.

**Стратегия объединения.** Вся библиотека использует `Multiply` для трения и `Maximum`
для упругости. Приоритет объединения в Unity:
`Average < Minimum < Multiply < Maximum`, поэтому при такой стратегии любая скользкая поверхность
доминирует в результате трения, а любой упругий материал доминирует в результате отскока —
что и ожидают люди интуитивно.

**Таблица поведения пар.** Вкладка Материалы рассчитывает каждую пару групп в вашем
проекте по реальным правилам приоритета Unity и показывает значение, которое фактически
применится, плюс понятный вердикт («цепкое / без отскока»). Это самый быстрый способ
ответить на вопрос «почему мой лёд не скользит».

**Автоназначение по имени.** Заполняет каждую группу из пресетов, сопоставляя имя группы
с английскими, китайскими и русскими ключевыми словами.

**Честное ограничение.** У `PhysicMaterial` есть четыре числа и два режима объединения. Он
не может выразить трение качения, анизотропное трение, вязкость, пластическую
деформацию, температуру или износ. «Реальные параметры» здесь означают таблицу
справочных значений и рабочие пресеты, а не физическую симуляцию.

<a id="sec-11"></a>
## 11. Диагностика покрытия

Вкладка Запекание отвечает на вопрос, который обычно решается наугад: **у каких треугольников
вообще нет выпуклого тела?**

Он берёт исходный меш в позе привязки и проверяет центроид каждого треугольника против
плоскостей каждого тела, сообщая:

- общий процент и полосу прогресса;
- разбивку по разделам;
- список непокрытых треугольников, отображаемый в окне Scene красным
  (**Показать непокрытые грани**).

Считайте значение ниже ~95 % проблемой: повысьте точность или проверьте, что кости разделов
действительно покрывают весь скелет.

<a id="sec-12"></a>
## 12. Состояние коллизий

Оценка из 100 со списком всех проблем и, где возможно, исправлением в один клик.

Проверки включают: ничего не запечено; выпуклое тело превышает предел вершин PhysX; тела близки к

<a id="sec-13"></a>
## 13. События и интеграция

Каждое событие несёт полный контекст, так что вам больше никогда не придётся ничего искать:

```csharp
public struct DycEvent
{
    public DycEventKind kind;          // CollisionEnter/Exit, TriggerEnter/Exit
    public int elementIndex;
    public string elementName;
    public Transform bone;             // the bone the hull is attached to
    public int groupIndex;
    public string groupName;
    public PhysicMaterial material;
    public Collider selfCollider;      // which of your hulls
    public Collider otherCollider;
    public Rigidbody otherBody;
    public GameObject otherRoot;
    public Vector3 point;
    public Vector3 normal;
    public float relativeSpeed;
    public float damageMultiplier;     // element × group
    public string eventName;
    public float time;
}
```

Три способа его использовать:

1. **UnityEvent** — `onEvent` на компоненте, для слушателей, зарегистрированных кодом.
2. **Реестр строк** — задайте разделу или группе имя события и слушайте через
   `Dyc_Events.Register("Hit.Head", handler)`. Опечатки в именах не вызывают ошибок, но
   проверка состояния сообщает о событиях, которые никто не получил.
3. **Статический фасад** — `Dyc_Api` для внешних инструментов:

```csharp
Dyc_Api.Register("Hit.Head", OnHeadHit);
Dyc_Api.GlobalEvent += e => Debug.Log(e.kind);
Dyc_Api.GlobalFilter = e => e.otherCollider.CompareTag("Friendly");  // swallow
Dyc_Api.Rebuild(gameObject);
Dyc_Api.SwapBaked(gameObject, otherSet);       // e.g. runtime precision switching
Dyc_Api.SetCollidersEnabled(gameObject, false);
Dyc_Api.GetStats(gameObject, out int parts, out int hulls);
```

Множители урона хранятся в разделе и в группе и перемножаются —
голова ×4 — это одно число, а не слой связующего кода.

**Дедупликация.** Перекрытие шва означает, что две соседние группы могут в одном кадре
коснуться одного и того же чужого коллайдера. NDC отправляет не более одного события на
`(element, other collider)` за кадр, поэтому разделённые материалы не дублируют события.

<a id="sec-14"></a>
## 14. Опрос триггеров

Unity доставляет обратные вызовы триггеров **на пару Rigidbody**, поэтому один рэгдолл — это одна
пара rigidbody, и физический слой просто не может сообщить, какая кость вошла в
объём. Назначение каждой кости собственного `Rigidbody` разрушило бы обещание нулевой стоимости.

Поэтому разделённые триггеры вместо этого сэмплируются:

- Каждый раздел проверяется с помощью `Physics.OverlapBoxNonAlloc` по границам в мировом
  пространстве его коллайдеров.
- Учитываются только настоящие триггеры и никогда — ваши собственные коллайдеры.
- Разделы обрабатываются порциями: `elements / frames-per-pass` за кадр.
- Вход и выход сравниваются с предыдущим проходом для каждого раздела.

**Семантика, которую нужно помнить:** это сэмплирование, а не событие. Очень быстрый пролёт может быть
пропущен. Повысьте частоту сэмплирования или используйте **sweep margin**, чтобы расширить область запроса.

<a id="sec-15"></a>
## 15. Масса, самоколлизия и LOD

**Масса из плотности.** NDC знает объём каждого выпуклого тела, поэтому может корректно вычислить массу:
`mass = hull volume × group density`, при желании нормализованную так, чтобы весь персонаж
соответствовал целевому суммарному значению массы. Это устраняет самую старую ручную работу в
рэгдоллах Unity. Один rigidbody получает сумму объёмов принадлежащих ему выпуклых тел.

**Самоколлизия.** `Ignore` (все пары), `Adjacent` (тот же раздел или предок и
потомок) или `On`. Столкновения костей рэгдолла друг с другом — частая причина
дрожания, и `Adjacent` — обычное решение. При более чем 200 коллайдерах этот шаг пропускается
с предупреждением, а не блокирует `Awake`.

**LOD.** `Disable` отключает коллайдеры за пределами расстояния; `Reduce` оставляет только
самое крупное выпуклое тело на раздел. Проверка выполняется каждый четвёртый кадр.

**Rigidbody.** Unity доставляет обратные вызовы коллизий только тому GameObject, которому принадлежит
`Rigidbody`. В рэгдолле оно уже есть у каждой кости. В любом другом случае включите
**Автодобавление Rigidbody**, и NDC создаст кинематический на объекте компонента.

<a id="sec-19"></a>
## 19. Решение проблем и FAQ

**Ничего не сталкивается, и события не срабатывают.**
В цепочке родителей нет `Rigidbody`. Unity отправляет обратные вызовы коллизий только
тому объекту, которому принадлежит rigidbody. Включите **Автодобавление Rigidbody** или добавьте его сами.

**Выпуклые тела не совпадают с тем, что я вижу.**
Гизмо по умолчанию рисует **позу привязки** — именно она была запечена. Отключите
**Bind pose** на вкладке Gizmo, чтобы увидеть их в текущей позе.

**«У выпуклого тела N вершин, что превышает предел PhysX в 255.»**
Unity молча игнорирует выпуклое тело сверх предела. Понизьте точность на одну ступень;
проверка состояния предлагает именно это как исправление в один клик.

**В некоторых местах попадания теряются.**
Сначала проверьте процент покрытия. Ниже ~95 % — это реальные дыры. Затем проверьте
**перекрытие шва** для вашей ступени точности.

**Мазок кисти оставил зазор между двумя регионами.**
Это проблема шва. Повысьте точность (что уменьшает перекрытие шва) или нарисуйте
немного за границей. Дедупликация в пределах кадра уже предотвращает двойные события
от перекрытия.

**События срабатывают дважды на одно попадание.**
В одном кадре были задеты два разных раздела, и это законно. Если вы действительно
хотите одно событие на пару объектов, фильтруйте по `elementIndex` в своём обработчике.

**Я нарисовал, но после запекания ничего не изменилось.**
Метки игнорируются, когда число треугольников не совпадает с исходным мешем —
обычно после повторного импорта или изменения топологии. Нарисуйте заново или сначала запеките, чтобы ассет
меток был создан правильного размера.

**Кисть не запускается.**
Запущен режим Play или окно Animation воспроизводит предпросмотр. Обе причины показаны как
явная причина на вкладке Кисть.

**Моя старая работа кистью исчезла после обновления.**
Так быть не должно: маски, созданные до появления флага рисования, мигрируются, а любая
ненулевая метка считается нарисованной. Если маска была очищена, нарисуйте и запеките заново.

**Действительно ли стоимость выполнения равна нулю?**
В установившемся режиме — да: выпуклые тела являются ассетами, трансформы отслеживаются иерархией, и
работы с мешами нет вообще. Единственная работа на кадр — необязательный опрос триггеров
и проверка расстояния для LOD.

**Можно ли разместить два компонента Dynamic Collision на одном объекте?**
Нет, и это заблокировано намеренно. Два компонента создали бы дублирующиеся выпуклые тела на
одних и тех же гранях, удвоили бы контакты и события. Разделяйте с помощью разделов и
групп материалов.

## 21. Обычное использование и паритет с RASCAL

### 21.1 NDC как системный коллайдер

Правило проектирования таково: разработчик, знающий `Collider` и `Rigidbody`, уже знает NDC, потому что NDC *создаёт* обычные коллайдеры: `MeshCollider` на скрытых дочерних объектах, `Rigidbody` на объекте, стандартные сообщения, обычные слои и физические материалы. `Physics.Raycast` и `Physics.OverlapSphere` не требуют никаких изменений.

```csharp
using NekoDynamicCollision;

void Start()
{
    Dyc_Collision.Attach(gameObject);      // добавить + собрать
    Dyc_Collision.SetMaterial(gameObject, myMaterial);
}

void OnCollisionEnter(Collision c) { }     // стандартное сообщение Unity
void OnTriggerStay(Collider other) { }     // стандартное сообщение Unity
```

| Вызов | Значение |
|---|---|
| `Find(go)` | Компонент, на объекте или на родителе |
| `Attach(go, generateNow)` | Добавить компонент и собрать |
| `Build(go)` / `Rebuild(go)` | Собрать из запечённого набора или сгенерировать в рантайме |
| `IsBuilt(go)` / `GetEnabled(go)` / `SetEnabled(go, v)` | Состояние, сразу для всех тел |
| `SetTrigger(go, v)` | `Collider.isTrigger` для каждого тела |
| `SetMaterial(go, pm)` | Немедленно; не переживает пересборку |
| `GetColliders(go)` / `ForEachCollider(go, a)` | Тела, как обычные `Collider` |
| `SetReceiver(go, t)` | Отправлять стандартные сообщения также в `t` |

**Дополнительно только зонирование.** Зоны, нарисованные материалы, LOD, события, масса из плотности и проверка состояния требуют API NDC — это то, чего системный коллайдер не умеет.

**Без шага запекания.** Включите **Advanced ▸ Build at startup when nothing is baked** (или вызовите `Attach`). Коллайдеры строятся по костям из меша в `Awake` — по одному выпуклому телу на кость, как в стандартном режиме RASCAL. Запекание остаётся способом получить зоны, декомпозицию, покрытие и точность.

**Сообщения, доходящие до вашего скрипта.** Unity доставляет `OnCollision*` объекту с `Rigidbody`. Если ваш скрипт находится в другом месте (корень персонажа, а `Rigidbody` на кости), задайте `Advanced ▸ Also send OnCollision*/OnTrigger* to` — тогда сообщения пересылаются через `SendMessage`, что не стоит ничего в кадрах без столкновений.

### 21.2 Живое обновление — возможность, которую запекание не заменит

Запечённое тело, приклеенное к кости, точно в позе привязки и жёстко после неё. При сильной деформации — приседание, сжатая конечность, натянутая ткань — тело неверно сообщает о поверхности. Живое обновление перестраивает тело из **текущей** позы скиннинга.

Включите его через **Advanced ▸ Live update** или `Dyc_Collision.EnableLiveUpdate(go)`.

| Настройка | По умолчанию | Значение |
|---|---|---|
| `liveUpdate` | выкл. | Перестраивать тела из текущей позы |
| `liveUpdateContinuous` | вкл. | Продолжать или выполнять один проход по запросу |
| `idleCpuBudgetMs` | 0.2 | Бюджет, пока меш почти не движется |
| `activeCpuBudgetMs` | 1.0 | Бюджет, пока он движется быстро |
| `meshUpdateThreshold` | 0.02 | Пропускать проход ниже этого движения (метры) |
| `maxColliderTriangles` | 5000 | Потолок на коллайдер, чтобы тяжёлая кость не съела бюджет |

Бюджет выбирается по тому, насколько меш действительно сместился, поэтому стоящий персонаж платит по тарифу простоя, а бегущий — по активному. Работа, которая не помещается, переносится на следующий кадр, а `OnUpdateYield` / `OnPassComplete` сообщают прошедшие миллисекунды.

**Он не перестраивает всё каждый кадр.** Три механизма делают стоимость предсказуемой:

1. **Инкрементально.** Центр каждого кластера сравнивается с предыдущим проходом, и перестраиваются только реально сдвинувшиеся кластеры. Мягкое тело, подвешенное на якоре, имеет дрожащую кромку и почти неподвижную середину — середина не стоит ничего.
2. **С приоритетом.** Очередь отсортирована по величине смещения каждого кластера. Если бюджет кончается, он кончается на самых спокойных кластерах — тех, где неточность наименее заметна. Без этого бюджет ушёл бы на то, что случайно оказалось первым в списке.
3. **Бюджет по часам**, а не по числу кластеров: стоимость на кадр не растёт с числом кластеров у тела.

`LastDirtyCount` и `LastBuiltCount` сообщают, что реально сделал последний проход, — это честный способ увидеть экономию.

```csharp
var live = Dyc_Collision.EnableLiveUpdate(gameObject);
live.OnPassComplete += ms => Debug.Log($"pass done in {ms:F2} ms");
live.StopAfterPass();          // завершить текущий проход и остановиться
live.UpdateNow();              // один полный проход, вне бюджета
```

**Требования.** Телам нужен `sourceVertices`, который записывает запекание; перезапеките старого персонажа, чтобы включить живое обновление. Стоимость в рантайме реальна — это единственная функция, противоречащая «нулевой стоимости на кадр», и именно поэтому она по умолчанию выключена.

### 21.3 Переопределения на кость

`Dyc_BoneProperties` ставится на саму кость (Add Component ▸ NekoWorks ▸ Dynamic Collision ▸ Bone Properties):

| Поле | Действие |
|---|---|
| `overrideMaterial` + `physicsMaterial` | Тела этой кости используют этот материал |
| `overrideConvex` + `convex` | Тело вместо поверхности (или наоборот) для этой кости |
| `overrideWeightThreshold` + `boneWeightThreshold` | Порог веса на кость |
| `exclude` | Никаких коллайдеров для этой кости |

Размещение на кости означает, что оно переживает переименования — оно хранит ссылку, а не путь.

### 21.4 Материалы по исходному материалу

`Advanced ▸ Materials by source material` сопоставляет исходный `Material` с `PhysicMaterial`. Тела приписываются по подмешу, из которого они в основном происходят, и это разрешается при запекании в `Dyc_BakedSet.sourceMaterials`. Приоритет, от высшего:

1. `Dyc_BoneProperties.physicsMaterial`;
2. сопоставление материала для исходного материала тела;
3. материал нарисованной группы.

### 21.5 Карта исключения вершин

`Advanced ▸ Exclusion map` читает канал текстуры (R/G/B/A, с порогом) и исключает вершины, значение канала у которых равно порогу или выше. Кисть помечает *грани*, карта помечает *вершины* — они дополняют друг друга. Мешу нужны UV, текстуре нужен **Read/Write Enabled**, а треугольник исключается только когда исключены все три его вершины.

### 21.6 Перенацеливание скелета

`Advanced ▸ Attach hulls to another skeleton` строит тела из этого меша, но вешает их на одноимённые кости другого корня — случай `RetargetSkeleton`, для Puppet Master и подобных схем. Кости разрешаются по относительному пути; тело без одноимённой пары остаётся на своём скелете, и отчёт запекания сообщает, сколько таких.

### 21.7 Мягкий режим — без костей, управляемый кодом или солвером

Мягкий режим (`Mode → Soft`) — **не** скелет со скиннингом. Он для меша **без скелета**, форма которого создаётся солвером или кодом, — NekoDynamicSoftbody и подобные. В мягком режиме ничто не читает кости; геометрия меша берётся как есть.

**Что создаёт запекание.** Меш делится на пронумерованные пространственные кластеры. Каждое тело строится *относительно центра своего кластера*, и центр сохраняется как поза покоя кластера (`clusterRest`). Именно это позволяет кадру перемещать **и вращать** тело как единое целое.

**Без солвера.** Кадры создаются в их позах покоя, поэтому тела ложатся точно на реальную геометрию меша и движутся вместе с объектом. Форма верна; просто нет динамики. Это задуманная деградация, а не сбой — и именно это означает «вычисляет реальную форму без NDSC».

**С солвером.** Солвер толкает кадры (`Push` → `Apply`) и полностью берёт управление, давая полную симуляцию. Адресуемый push не перезаписывается глобальным опросом в том же кадре, что важно, как только существует больше одного тела.

**Живое обновление работает и без скелета.** `Dyc_LiveUpdate` читает CPU-вершины `MeshFilter` как есть, поэтому любой код, деформирующий меш — солвер мягкого тела, процедурный скрипт, собственный деформер, — приводит в движение точные тела без специфичной для плагина связки. Телу нужен `sourceVertices`, который записывает запекание; перезапеките старый ассет.

**Честный предел:** деформация, существующая только на GPU (вершинный шейдер, GPU-скиннинг), не может быть прочитана обратно на CPU, поэтому живое обновление её не видит. Перенесите деформацию на CPU или сохраните запечённые тела.

### 21.8 Управление отдельными телами

```csharp
int n = component.HullCount;
for (int i = 0; i < n; i++)
{
    Collider c = component.HullCollider(i);
    int hullIndex = component.HullIndexOf(c);
    DycBakedHull hull = component.BakedSet.hulls[hullIndex];
}
```

`HullCollider`, `HullIndexOf`, `HullCount`, `BakedSet`, `Elements` и `Groups` открыты, поэтому внешние инструменты могут перебирать и управлять отдельными телами без рефлексии.

## Приложение B. Проверки физики проекта

Проверка состояния анализирует настройки `Physics` проекта, потому что пресет материала
не может исправить глобальную настройку:

| Настройка | Почему это важно |
|---|---|
| `bounceThreshold` | Удары медленнее этого значения никогда не отскакивают. При стандартном значении Unity 2 пресет резины выглядит сломанным. Понизьте его до 0.2–0.5, чтобы использовать упругие материалы. |
| `defaultSolverVelocityIterations` | При значении 1 стеки и быстрые удары дрожат или проходят насквозь. 2–4 обычно лучше, и это частая первопричина дрожания рэгдолла. |
| `gravity` | Если оно не равно −9.81, все интуитивные представления о массе и импульсе, выведенные из −9.81, ошибочны на тот же коэффициент, и пресеты плотности требуют коррекции. |
| `defaultContactOffset` | Большой зазор контакта заставляет тонкие объекты выглядеть парящими. |

Применение рекомендованных значений — действие в один клик со вкладки Материалы или из
проверки состояния.
